# LokalEats — Project Documentation

> Read this file first. It captures the full current state of the project, why things are built the way they are, and what's still pending — so a new session doesn't have to re-derive any of it.

## TL;DR — Quick Orientation

- **What it is**: A content-based dish (not restaurant) recommender for Perak, Malaysia. University project — demoed locally, minimal auth, no build step on the frontend.
- **Stack**: FastAPI + SQLite backend, scikit-learn cosine-similarity recommender, OpenRouter LLM for two narrow features only (never for ranking), vanilla HTML/CSS/JS frontend (no framework).
- **Current state**: Fully functional, running locally at `http://127.0.0.1:8000`. Git initialized with one commit (`9edb774`) — **not yet pushed to any remote**. Uncommitted working-tree changes exist from the most recent session (onboarding wizard simplification, gamification/achievements system) — see [Session History](#session-history--changelog) for what's uncommitted.
- **Deployment**: Prepared for Render (not Vercel — Vercel's serverless read-only filesystem is incompatible with SQLite writes). `render.yaml` is ready; pushing to GitHub + connecting Render is the next step whenever the user wants to resume that thread.
- **Data**: Real 928 restaurants (`perak_restaurant.csv`) + synthetic 2,844 dishes mapped onto them (`dishes.csv`), both already in the repo root.

## System Architecture

```
┌──────────────────────────────────────────────────────────┐
│                         Browser                              │
│     static/index.html + app.js + style.css (vanilla JS)      │
│     Leaflet.js maps embedded inline in Recommend & Search     │
└────────────────────────────┬──────────────────────────────────┘
                              │ fetch() — JSON over HTTP, same origin
                              ▼
┌──────────────────────────────────────────────────────────┐
│                    FastAPI app (main.py)                     │
│  Loads DISH_DF (pandas) + DISH_MATRIX (numpy) ONCE at         │
│  startup — cached in memory for the lifetime of the process.  │
│  All /api/* routes read from this cache; only writes touch    │
│  SQLite directly (users, ratings, llm_cache tables).           │
└───────────┬──────────────────────────────┬────────────────────┘
            │                              │
            ▼                              ▼
┌─────────────────────┐         ┌─────────────────────────────┐
│   recommender.py       │         │           llm.py               │
│   Pure functions:         │         │  OpenRouter chat completions    │
│   build_dish_matrix()       │         │  explain(user, dish) → 1 line    │
│   build_user_vector()         │         │  parse_query(text) → filter JSON │
│   recommend()                   │         │  Never selects/ranks dishes —     │
│   similar_dishes()                │         │  gracefully returns                │
│   No I/O — takes DataFrames         │         │  {"error":"llm_disabled"} if       │
│   and returns DataFrames              │         │  no OPENROUTER_API_KEY set          │
└─────────────────────┘         └─────────────────────────────┘
            │
            ▼
┌─────────────────────┐
│    lokaleats.db         │
│  SQLite, 5 tables:         │
│  restaurants, dishes,        │
│  users, ratings, llm_cache      │
└─────────────────────┘
```

**Key architectural decision**: the dish feature matrix is built once at process startup (`main.py` module load, not per-request). This is why `main.py` refuses to start if `lokaleats.db` doesn't exist yet — it needs the data at import time, not lazily. This also means **any change to `dishes.csv`/`perak_restaurant.csv` requires re-running `seed_db.py` AND restarting the server** — the in-memory cache won't pick up DB changes made by another process while the server is running.

## Data Model

### Source CSVs (already in repo root — do not regenerate)

**`perak_restaurant.csv`** — 928 rows: `name, category, all_categories, address, city, postal_code, latitude, longitude, phone, price_range, rating, reviews_count, website, gmaps_url, place_id, district`. `place_id` is the join key. Some `rating`/`price_range` are null — handled everywhere with `_clean()` in `main.py`.

**`dishes.csv`** — 2,844 rows: `dish_id, dish_name, price_rm, spice_level, halal, tags, cuisine_profile, restaurant_name, place_id, city, district, restaurant_rating, latitude, longitude`. `halal` is one of `halal` / `non-halal` / `unknown` — **`unknown` is deliberately excluded when a user filters halal-only** (conservative labeling, not a bug).

### SQLite schema (`seed_db.py`)

```sql
CREATE TABLE restaurants (place_id TEXT PRIMARY KEY, name, category, address, city, district, latitude, longitude, phone, price_range, rating, reviews_count, gmaps_url);
CREATE TABLE dishes (dish_id TEXT PRIMARY KEY, dish_name, price_rm, spice_level, halal, tags, cuisine_profile, place_id REFERENCES restaurants);
CREATE TABLE users (user_id INTEGER PRIMARY KEY AUTOINCREMENT, name, budget_max, spice_pref, halal_only, cuisines, tags_pref);
CREATE TABLE ratings (user_id, dish_id, liked, created_at, PRIMARY KEY (user_id, dish_id));
CREATE TABLE llm_cache (dish_id, user_id, text, created_at, PRIMARY KEY (dish_id, user_id));
```

`ratings.liked` is now **always 1** in practice — see [Star System](#star-system-not-likedislike) below for why. `seed_db.py` drops + recreates **all five tables** on every run, so it wipes user/rating/star history too — this is intentional for reproducible demos but means don't run it against a DB you want to preserve.

### Feature vector (34 dimensions, built once in `recommender.py`)

| Segment | Dims | Values |
|---|---|---|
| Cuisine one-hot | 11 | `malay, chinese, tomyam, seafood, kopitiam, cafe, western, indian, burger, bakery, cendol` |
| Tags multi-hot | 18 | `breakfast, rice, noodle, soup, seafood, western, dessert, drink, dinner, lunch, grilled, fish, burger, salad, healthy, pastry, snack, side` |
| Price | 1 | min-max normalized across all dishes |
| Spice | 1 | `spice_level / 3` |
| Halal one-hot | 3 | `halal, non-halal, unknown` |

User vectors live in the same 34-dim space: preferred cuisines/tags → 1, budget → normalized `0.6 × budget_max` (users prefer dishes comfortably under budget, not right at the limit), spice_pref → `/3`, halal_only → sets the `halal` one-hot dim to 1 (otherwise all halal dims stay 0, i.e. no preference signal).

## Recommendation Algorithm

**This is content-based filtering, not collaborative filtering** — see the answer already given in conversation about why, worth preserving here since it's a legitimate thing to get right in a report/viva:

1. **Hard filters first** (never ranked away — a dish either passes or is excluded before scoring):
   - `price_rm <= budget_max`
   - `halal_only` → keep only `halal == "halal"` (excludes `unknown`)
   - optional `district` exact match
   - optional `max_km` via haversine distance from `(lat, lng)`
2. **Score** (only computed on dishes that passed the filters):
   ```
   score = 0.7 × cosine_similarity(user_vec, dish_vec)
         + 0.2 × (restaurant_rating / 5, default 3.5 if null)
         + 0.1 × tag_overlap_with_users_own_starred_dishes   [if user has ≥1 starred dish]
   ```
   If the user has never starred anything, the 0.1 weight redistributes: `0.8 × similarity + 0.2 × rating`.
   A small deterministic hash-based tie-breaker (`hashlib.md5(dish_id)`) is added so equal scores don't always sort identically.
3. **`similar_dishes(dish_id, k)`** — nearest-neighbor cosine similarity to one dish's vector, excluding the dish itself and same-`dish_name` duplicates at other restaurants (used by "More like this").

The `tag_overlap` term is the **only personalization signal**, and it only ever looks at *that single user's own* starred dishes — never other users' data. That's why this isn't collaborative filtering even though it does adapt to behavior.

## API Reference

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/users` | Create user from onboarding payload |
| GET | `/api/users/{id}` | Fetch user |
| GET | `/api/recommend` | Main recommend query — params: `user_id`, `district`, `lat`/`lng`/`max_km`, `max_price` (overrides user's stored budget for this query), `k` |
| GET | `/api/dishes/{id}/similar` | Item-item nearest neighbors |
| POST | `/api/rate` | Star (`liked:true`) or unstar (`liked:false`, **deletes the row**) a dish |
| GET | `/api/starred` | All currently-starred dishes for a user, most-recent-first |
| GET | `/api/dishes` | Browse/filter (search text, district, cuisine, halal, max_price) — not currently used by the frontend UI but kept as a general endpoint |
| GET | `/api/districts` | District list with dish counts (populates the district `<select>`) |
| POST | `/api/explain` | LLM one-liner explanation, cached in `llm_cache` table |
| POST | `/api/nlq` | LLM parses free-text query → filter JSON → runs through `recommend()` |
| GET | `/` | Serves `static/index.html` |

Every endpoint returns JSON on error (global exception handler in `main.py`), never a 500 HTML page.

## Frontend Architecture

### Views (all in one `index.html`, toggled by JS adding/removing `.active`)

1. **`#view-landing`** — dark hero, animated blob background, Playfair Display headline, animated stat counters, cuisine marquee. Entry point.
2. **`#view-onboarding`** — **2-step wizard** (was originally 3 steps; spice level and Halal-only toggle were removed per explicit user request — see Session History):
   - Step 1: name + budget slider
   - Step 2: cuisine chips + craving/tag chips
   - `spice_pref` defaults to `1` (`DEFAULT_SPICE_PREF` constant) and `halal_only` defaults to `false` — both hardcoded now, never asked upfront. Spice level is still shown on every dish card; it just isn't collected as a preference anymore.
3. **`#view-recommend`** — district filter, budget slider filter (separate from the onboarding budget — this one re-queries live via `max_price` param, debounced 350ms), "Near me" geolocation button, List/Map toggle.
4. **`#view-search`** — natural-language query box, example query chips, shows parsed filter chips for transparency, same List/Map toggle pattern as Recommend.
5. **`#view-starred`** — Achievements panel (see [Gamification](#gamification--achievements)) + grid of starred dishes.

### State (`app.js`, single `state` object)

```js
state = {
  userId, userName, wizardStep,
  selectedCuisines: Set, selectedTags: Set,     // onboarding chip selections
  recDishes: [], searchDishes: [],               // last-rendered results per view
  starredIds: Set, starredDishesMap: Map,        // dish_id -> full dish object, for badge computation
  maps: { rec: {instance, markers}, search: {instance, markers} },  // two independent Leaflet instances
}
```

`starredDishesMap` is the source of truth for achievement badges — rebuilt fully from `/api/starred` on page load, updated incrementally (add/delete single entries) on every star/unstar so badges update live without a re-fetch.

### Maps are embedded, not a separate page

Originally a third nav tab, merged into Recommend and Search directly per user request — each view has its own List/Map toggle (`.view-toggle` buttons) and its own `.map-container` div. Two independent Leaflet map instances exist (`state.maps.rec`, `state.maps.search`) so switching between Recommend/Search doesn't clobber the other's map state. `refreshMap(view)` groups dishes by `place_id`, keeps the highest-scoring dish per restaurant, and drops a marker with a popup linking to `gmaps_url`.

### Star system, not like/dislike

Originally 👍/👎 buttons writing `liked: 1/0` to the `ratings` table. Changed per user request: **dislike removed entirely**, like became a single ⭐ toggle. Unstarring now **deletes the row** from `ratings` (not `liked=0`) since a negative rating no longer has meaning in a star-only system. `POST /api/rate` still takes the same `{user_id, dish_id, liked}` shape — `liked:false` just means "delete" now instead of "downvote".

### Gamification / Achievements

Lives entirely in the Starred view, computed client-side from `state.starredDishesMap` — **no backend changes needed** for this feature:

| Badge | Type | Logic |
|---|---|---|
| 🍜 Cuisine Explorer | Progress bar | distinct `cuisine_profile` values among starred dishes, out of 11 |
| 📍 District Hopper | Progress bar | distinct `district` values among starred dishes, out of 10 |
| ⭐ First Star | Binary unlock | ≥1 starred dish |
| 🌶️ Brave Eater | Binary unlock | any starred dish has `spice_level === 3` |

`computeBadges()` → `renderAchievements(badges)` updates the DOM; `announceNewBadges(before, after)` compares snapshots taken immediately before/after a star action and fires staggered celebratory toasts (700ms + 500ms per message) for anything that just crossed a threshold. This is explicitly scoped as **session-level momentum, not permanent achievements** — there's no login persistence, so badges reset whenever a new user is created (page refresh = re-onboard, matches the original "no auth complexity" spec).

### Dish card images

Neither CSV has real photo URLs. Instead of a generic placeholder, each card gets a **cuisine-themed gradient banner + matching emoji** (`CUISINE_EMOJI` map in `app.js`, 11 distinct gradients in `style.css` keyed by `.dish-image.cuisine-{name}`). This was a deliberate substitute for real images, not a temporary stopgap — there's no image data anywhere in the pipeline to eventually swap in.

## System Flow (key request sequences)

### Onboarding → first recommendations
```
User fills Step 1 (name, budget) → Step 2 (cuisines, tags) → clicks "Find my dishes"
  → POST /api/users {name, budget_max, spice_pref:1, halal_only:false, cuisines, tags_pref}
  → user_id stored in state
  → recBudgetSlider synced to user's budget_max
  → GET /api/districts (populates dropdown)
  → GET /api/recommend?user_id=X&k=12
  → renderGrid() into #rec-grid
```

### Recommend query (any filter change)
```
User changes district / drags budget slider / clicks "Near me"
  → loadRecommendations(extraParams) called with whatever changed
  → GET /api/recommend?user_id=X&district=...&max_price=...&lat=...&lng=...&max_km=15&k=12
  → main.py: user_row_to_dict() → optionally overrides budget_max with max_price
             → get_liked_tags() reads user's own starred dishes for the tag-overlap term
             → recommender.recommend() applies hard filters, then scores, then top-k
  → dish_row_to_dict() per result (NaN-safe via _clean())
  → frontend renders grid; if Map mode was active, refreshMap('rec') also fires
```

### Natural-language search
```
User types free text → POST /api/nlq {user_id, query}
  → llm.parse_query() → OpenRouter → strict JSON {max_price, spice_min, district, cuisine, tags, halal_only}
  → if llm_disabled or parse fails, returns {"error": ...} — frontend shows a friendly message, no crash
  → on success: main.py merges parsed filters into the user's profile (union, not replace, for cuisines/tags)
  → runs the SAME recommender.recommend() as the main recommend endpoint
  → returns {parsed_filters, results} — frontend renders parsed_filters as removable chips (transparency)
```

### Star / unstar + badges
```
Click ⭐ Star on any card
  → toggleStar(dish, btn, card): compute badgesBefore, mutate state.starredIds + starredDishesMap,
    compute badgesAfter, renderAchievements(badgesAfter) immediately (optimistic UI)
  → POST /api/rate {user_id, dish_id, liked}
      liked:true  → INSERT/UPDATE ratings SET liked=1
      liked:false → DELETE FROM ratings WHERE user_id=? AND dish_id=?
  → toast confirms; announceNewBadges(badgesBefore, badgesAfter) fires any newly-crossed achievement toasts
  → if unstarring FROM the Starred page specifically, the card fades out and removes itself from the DOM
```

## LLM Integration

`llm.py` has exactly two entry points, both optional (app is 100% functional without an API key):

- **`explain(user, dish)`** — one casual Manglish sentence explaining a recommendation. Cached per `(dish_id, user_id)` in the `llm_cache` table so repeat views don't re-call the API.
- **`parse_query(query)`** — free text → strict filter JSON. Strips markdown code fences defensively before `json.loads()`.

Both return `{"error": "llm_disabled"}` immediately if `OPENROUTER_API_KEY` is unset — checked in `main.py` before any LLM call, so the rest of the app (`/api/recommend`, `/api/starred`, everything else) never depends on it.

**Model history — important context**: the original spec called for `meta-llama/llama-3.3-70b-instruct:free`. During testing this hit **persistent upstream rate limits on OpenRouter's free tier** (confirmed via direct API calls returning 429s with `retry_after_seconds` — a demand issue on OpenRouter's side, not a bug in this code; the request/auth/parsing pipeline was verified correct by routing the same prompts through a different model and getting clean responses). The model was switched to `google/gemini-2.5-flash-lite` (~$0.00002/call, effectively free) to get reliable responses for demos. If reverting to the spec'd free Llama model is ever required, only `MODEL` in `llm.py` needs to change — no other code depends on which model is configured.

## Design Decisions & Constraints (things to not "fix")

- **No collaborative filtering** — explicit constraint from the original spec. The only personalization is the tag-overlap term from a user's *own* stars.
- **LLM never selects or ranks dishes** — only explains picks already chosen by `recommender.py`, or translates free text into filter JSON that then goes through the same hard-filter + scoring pipeline as every other query.
- **`unknown` halal status is excluded from halal-only filtering** — conservative by design, not a data quality bug.
- **No persistent login** — page refresh = re-onboard. This is why achievements are described as session momentum, not permanent unlocks.
- **No real dish photos** — cuisine-themed gradient + emoji banners are the deliberate final design, not a placeholder awaiting real images.
- **`seed_db.py` wipes users/ratings on every run** — expected and fine for a demo; don't add migration logic to preserve data across reseeds unless explicitly asked.

## Deployment Status

- **Platform decision**: Vercel was considered and explicitly rejected — its serverless functions have a read-only filesystem (except an ephemeral, per-request `/tmp`), which is incompatible with the app's constant SQLite writes (new users, stars, LLM cache). **Render** was chosen instead: a normal long-running process with SQLite working unmodified.
- **`render.yaml`** is prepared as a Blueprint: `buildCommand` runs `pip install -r requirements.txt && python seed_db.py` (re-seeds the DB fresh on every deploy — free tier disk is ephemeral anyway, so this is a feature not a workaround), `startCommand` runs `uvicorn main:app --host 0.0.0.0 --port $PORT`. `OPENROUTER_API_KEY` is marked `sync: false` so it's entered manually in Render's dashboard, never committed.
- **Git**: initialized locally, `.gitignore` correctly excludes `.env`, `lokaleats.db`, `__pycache__/`, `.DS_Store`, and `.claude/` (Claude Code's local settings — not app code). One commit exists (`9edb774`). **No remote configured yet — nothing has been pushed anywhere.**
- **Remaining steps** (require the user's GitHub/Render accounts, can't be done unilaterally): create a GitHub repo → `git remote add origin ... && git push` → Render dashboard → New Blueprint → connect repo → paste API key → deploy.
- Expect ~30-60s cold start on the free tier after ~15 min idle — normal, not a bug.
